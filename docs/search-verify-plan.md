# 检索精确复核修复计划

> **状态(2026)**:已经选定并落地「FTS 为唯一匹配标准,应用层只展示高亮」这条路线。
> 应用层的二次精确复核已被删除:`documents_fts MATCH` + 结构化过滤即最终命中判定,
> `locate_literals` 只服务高亮与导航,不再否决结果。本文其余内容保留为当初的排查记录与
> 备选路线分析;其中「应用层复核」相关的条目(B1、B2、B6 等)已被本次改造重新归类,
> 仅剩查询正确性(B4/B5/B7)、展示定位(B3)、计数与 tokenizer/排名等独立问题
> 留待后续任务。

本文汇总对 `main`(`4ad57ab`)检索路径的排查结论与修复方案。所有缺陷均已在本地用 CLI 与
临时探针程序复现。

方案要点:把「FTS 表达式 + 扁平 literals」这套两处独立演化的逻辑,收敛成**一棵可执行树 +
若干机械派生**,把「精确语义」的实现收在一处;然后把「叶子欠召回」和「候选预算」这两个
与布尔结构无关的正确性问题单独处理。

## 术语与语义来源

rsou 是本仓库这一款 Rust 桌面检索工具。**wsou 是另一个产品**(TypeScript 版),rsou 在早期
阶段移植了它的查询语法与 tokenizer 语义作为起点。两者不是同一个程序,本计划里的行为判断一律
以 rsou 自身的代码与实际输出为准。

rsou 的语义规范原文在 `docs/plan.md`(§6.1 tokenizer 规范、§6.4 片段与高亮),该文件已在
`044a343`「清理仓库中的本机配置与内部文档」中删除,但 `src/` 下仍有十余处引用它(包括
`src/search.rs:10` 的「与 plan §6.4 的收口规则一致」)。修复期间需要定夺:`docs/plan.md` 里
仍然有效的约定(空白不参与比对、标点不剔除、`文 档` 命中而 `文、档` 不命中)是转写到本计划
或新的语义文档,还是从源码注释中删除引用。

本文沿用的关键约定:

- **精确模式**:按输入内容整体查找;空白/换行不参与比对,标点等其余字符不剔除。
- **宽松模式**:jieba 切词,各段之间 AND,段内同义词变体之间 OR。
- `title:` / `content:` 限定字段;`-x` / `NOT x` 排除;`OR` 取并。

| 编号 | 问题 | 类型 | 影响面 |
| --- | --- | --- | --- |

## 二、阶段划分

## 三、P1:扫描器与计数

### 3.1 全量枚举空白不敏感匹配

文件:`src/search.rs` 的 `locate_literals`(约 L146)与 `find_ignoring_whitespace`(L181)。

当前是两条路径:先 `match_indices` 找直接匹配,再 `find_ignoring_whitespace` 找一处空白不敏感
匹配。一个完整的空白不敏感枚举器已经覆盖直接匹配,不需要保留两条路径。改成单一实现:每次命中后
从上一处匹配的**起点**之后继续扫描(以枚举重叠),literal 的归一化(去空白、ASCII 折叠)在每次
扫描前做一次,推进按字符边界并正确还原切片基址。

验收:
- `文 档\n\n文 档` → 2 次出现;`文 档 文 档` → 2 次出现;`哈哈哈哈` 搜 `哈哈` → 3 次出现;
- 现有 `streaming_whitespace_matches_legacy`(L710)保留,比较对象改成「全量结果」;
  `legacy_whitespace_scan` 仍作差分基准。

### 3.2 片段真实总数

文件:`src/search.rs` 的 `group_into_fragments`(L266)。

`groups`(L309)在截断前已含真实片段数。让函数返回:

```rust
struct FragmentResult {
    hits: Vec<Hit>,
    total: usize,
}
```

（内部类型,**不需要 `pub`**。）物化循环取前 `limit` 个,`total` 取截断前的 `groups.len()`;
`src/search.rs:539` 的 `total_for_doc` 取 `fragments.total`。

注意当前循环在 `content.get(start..end)` 为 `None` 时会 `continue`,即异常边界下会跳过后补足;
直接改成 `take(limit)` 会改变这种填充行为。要么在注释中明确「块边界合法、各组可物化」这条前提,
要么沿用跳过后补足的逻辑。

`src/search.rs:567` 的汇总改用 `doc.total_hits`:

```rust
let total_hits = documents
    .iter()
    .filter(|hit| hit.group_id == hit.document.id)
    .map(|doc| doc.total_hits)
    .sum();
```

同步项:
- `DocumentHit.total_hits` 注释与 `SearchResponse.total_hits` 注释按实际口径重写;
- `src/search.rs:663` 的 `legacy_group_into_fragments` 与 `fragment_cursors_match_legacy`
  (L812)、`fragment_cursor_benchmark`(L869)跟随签名调整;
- 仅标题命中的文档 `hits` 为空时,`total_hits` 保持 0 会显示「命中 0 处」。GUI 与 CLI 的
  文案对这种情况改为「标题命中」,并在阶段二接入字段信息后一并处理。

区分三个计数概念,不要互相替代:**出现次数**(span 数)、**合并高亮区间数**(合并后的 span 数)、
**展示片段数**(`hits.len()`)。`total_hits` 是**截断前的匹配片段总数**(不是 `hits.len()`);
`response.total_hits` 是已返回代表文档的完整片段数之和——相对于**未返回的结果**才是下界。

## 四、P2:Plan 树

### 4.1 类型

`src/query.rs` 新增可执行树。`CompiledQuery` 加了私有字段与候选类型,属于 API 变更(当前
`src/app/workers.rs:962` 直接构造它),测试桩需要同步调整。

```rust
pub struct CompiledQuery {
    pub match_expr: String,   // 候选表达式,由 plan 派生
    pub literals: Vec<String>,// 正向叶子扁平去重(预览高亮的兜底)
    plan: Plan,               // 唯一语义载体,只读暴露
}

enum Plan {
    Leaf { field: FieldSpec, variants: Vec<String> },
    All(Vec<Plan>),
    Any(Vec<Plan>),
    Not(Box<Plan>),
}

enum FieldSpec { Title, Content, Any }
```

约束:

- `All([])` 为真,`Any([])` 为假;常量化简需覆盖 `All` 遇空集、`Any` 遇全集、`Not(True/False)`;
- 构造阶段完成规范化:单子节点塌缩、同类嵌套合并、直接双否定消除;
- `Has_positive`(`src/query.rs:80`)的校验作用在**源 AST** 上,不在规范化后的 plan 上;
- `variants` 不得为空;
- 宽松切词产出 `All(各段 Leaf)`,每个 `Leaf.variants` 内部是 OR。不允许把各段合并进同一个
  `variants`(会变成「各段各自存在」而非「段间 AND」);
- 显式字段优先于字段组,字段组优先于 scope,全部在构造阶段定下,`FieldSpec::Any` 表示
  scope=all 且无显式字段。

`match_expr` 与 `literals` 都是 plan 的派生视图,最好通过只读接口暴露,避免调用方修改后与
plan 不一致。当前 `src/app/workers.rs:962` 直接构造 `CompiledQuery`,该测试桩应改成构造函数
或 `#[cfg(test)]` 桩方法。

**不做否定范式(NNF)转换。** `Not` 保留任意子树,直接递归求值。理由是 NNF 会带来三个额外
代价,而收益不足:

1. NNF 后逐个 `Or` 分支检查正向条件,会拒绝原本合法的查询。反例 `合同 -(文档 -草稿)` 当前的
   合法语义是 `合同 AND NOT(文档 AND NOT 草稿)`;规范化成 `All(合同, Any(Not 文档, 草稿))` 后,
   内层 `Any` 的负分支会被「OR 两侧都要有正向条件」拒绝,但外层 `合同` 已经提供了安全锚点。
   删掉「在规范化树上逐个 OR 执行语法检查」即可,`has_positive` 仍只看源 AST。
2. NNF 抹掉「该叶子来自源排除子树」这一来源信息,而同义词展开策略与高亮策略都依赖它。
3. 保留任意 `Not` 子树后,候选派生与求值都只需一条「遇 `Not` 返回全集 / 不输出 span」的规则,
   不需要额外标记来源。

规范化仍执行:单子节点塌缩、同类嵌套合并、直接双否定消除(`Not(Not(x)) → x`)。

### 4.2 候选派生

候选表达式由 plan 自底向上生成,不另写一套编译逻辑:

```text
candidate(Leaf)   = FTS 短语(变体组展开成 OR)
candidate(Not X)  = 全集
candidate(All xs) = AND(candidate(xs)),丢弃全集子项
candidate(Any xs) = OR(candidate(xs))
```

`candidate(Not X) = 全集` 把否定从 FTS 移到应用层。之前的方案写成「删掉 NOT 分支」,对
`Any(A, Not B)` 会得出 `A`,而正确候选是全集。

候选类型显式化,空串不能充当全集:

```rust
enum Candidate { Match(String), AllDocuments, Empty }
```

约束:

- **不安全变体使整个变体组 OR 的候选变成全集**,不能只保留安全变体(那会漏召回);
- `AllDocuments` 的扫描范围仍是符合结构化过滤条件的可检索文档,不是整库;
- 没有 `MATCH` 时不存在可用的 BM25 排名,需要另定稳定排序(如 `documents.id`);
- 此处的「否定必须由应用层执行」是当前近似候选方案下的选择。若将来某个谓词能证明索引匹配
  与精确语义完全等价,它的否定理论上可以安全下推,本轮不做这种优化。

### 4.3 求值产出判据与 span

```rust
fn scan_eval(&self, title: &str, content: &str) -> Option<FieldSpans>
```

`FieldSpans` 按字段分别携带 span。约定:

- `Some(空)` 表示「成立但无可展示的正向证据」。典型情形是负叶不存在因此 `Not` 成立——
  **不是“同义词只命中了负向侧”那种描述**(那通常会使排除条件失败)。字段限定也不应让一个
  成功的正叶没有任何分字段 span;出现这种情况说明求值实现漏收了证据;
- `All` 失败时丢弃该分支已累积的 span;
- `Any` 收集**所有**成立分支的 span,不能首个成功就返回;
- `Not` 子树参与布尔求值,不输出 span,也不进 `literals`;
- `FieldSpec::Any` 的叶子需要同时扫标题与正文才能给全高亮;
- 叶子扫描复用同一 literal 的结果,避免反复扫全文。

`src/search.rs:525-529` 的两行替换为一次 `scan_eval`;标题与正文各自的 span 直接用作
`title_highlights` 与片段输入。

**预览也必须改用求值结果,不能继续扫扁平 `literals`。** `src/app/page_search.rs:647-664` 当前
用 `compiled.literals` 对预览窗口做 `locate_literals`,会与结果高亮不一致:

- `title:合同` 时正文里的「合同」不应成为证据,预览却会高亮;
- `(合同 发票) OR 草稿` 且正文含「合同 草稿」时,结果只输出「草稿」,预览会高亮两者。

改为使用该文档完整求值产生的正文 spans(按字段、只含成功分支)。不要在预览窗口上重求整棵树——
另一条 AND 条件可能落在窗口之外。`PreviewSpanCache` 的键要从 `literals` 换成这套字段感知的
证据。`locate_literals` 保留 `pub` 签名,退化为仅供无求值结果时的内部兜底。

### 4.4 编译期修复

**字段覆盖**(`src/query.rs:321` `apply_field`)。当前无条件写 `field: Some(field)`,改成
保留内层已有字段:

```rust
Node::Term { text, field } => Node::Term { text, field: field.or(Some(inherited)) },
```

对 `Phrase`、`Not`、`And`、`Or` 的递归同理。

**否定转换**(`src/query.rs:605` `compile_exclusion`)。该函数当前的错误是把排除侧的 `AND/OR`
原样保留,`-文档 -草稿 合同` 因此编译成 `合同 NOT (文档 AND 草稿)`,变成「同时含两者才排除」。
修复后 `Plan::Not` 直接承载子树,`compile_exclusion` 随之删除。

需要定死的顺序(建议按此实现):

1. 消除直接双否定;
2. 根据**源排除子树**确定同义词展开策略;
3. 展开成执行树;
4. 可选的布尔规范化(单子节点塌缩、同类嵌套合并)。

步骤 2 必须在展开之前,否则来源信息丢失:`A -(B - 电脑)` 里的「电脑」在布尔上处于正极性,
按极性决定展开就会与 `--电脑` 一致,破坏现有的「排除子树不展开同义词」约定。

**高亮策略与同义词策略同时定下**:凡出现在源排除子树中的叶子都不输出 span。两项不能分开定,
否则会出现「不展开但高亮」这类组合。

其他需要一并处理的:

- 字段前缀后的否定:`title:-合同` 当前在 `parse_primary` 报「缺少词语」。`-title:合同` 与
  `title:-合同` 应等价。同一处还要决定是否支持 `title:-(a b)`。

### 4.5 宽松模式标点段

`src/dict.rs:217` 的 `cut_loose` 只过滤空白,`文、档` 因此切出 `[文, 、, 档]`,而 tokenizer
丢弃顿号,条件恒不成立。

修复:在 `cut_loose`(或 `src/query.rs` 的切词包装层)过滤纯标点与符号段,引号短语保留原文。
这属于查询语言规则,**不能绑定当前 tokenizer 是否产出词元**——否则 P4 让顿号开始产词元后,
同一条 `文、档` 的语义会随索引版本变化。

过滤后没有任何有效段时,返回中文 `QueryError`,不能生成 `All([])`(那会变成恒真的空查询)。

验收:`文、档` 宽松模式的 `match_expr` 不含 `"、"` 片段,且该结果在 P4 前后一致。

### 4.6 CLI 参数

`src/bin/cli.rs:133` 用 `positional.get(1)` 取查询,其余位置参数被忽略,以 `-` 开头的参数还会
先被当成选项。所以只加 `--` 分隔符不够:

```
search -- -文档 合同      # 仍可能只把 -文档 交给查询解析器
```

保持「一个查询字符串」的简单接口,并明确示例:

```
rsou-cli search --scope content -- '-文档 合同'
```

`--` 之后停止识别所有选项(`--scope`、`--help` 等);多余的位置参数报错,不静默忽略。若以后要
支持多参数拼成查询,必须另定拼接规则。

## 五、P3:候选安全退路与预算

### 5.1 叶子欠召回

`locate_literals` 是子串语义,ASCII 词元是整段匹配。已实测:`doc` 对 `docx`、`document` 对
`docu ment`、`"docu ment"` 对 `document`、`😀` 对 `😀` 都是精确定位命中、FTS 候选为 0。

可选方向:

1. **保留现有语义声明,建设安全退路**(建议)。不能证明安全的叶子退为全集;同一查询里有安全
   锚点(如 CJK 条件)则继续利用。安全退路本来就能同时满足「子串」「忽略空白」「候选超集」
   三件事,下面第 5.2 段的「不能同时承诺三件事」只在「每个叶子都原样下推当前 FTS 短语」时
   成立。
2. 收窄语义声明:ASCII 与符号按词元边界匹配,CJK 逐字且标点敏感。这不是更小的修复——当前
   符号根本没有词元,ASCII 内部空白如何处理也未定义,相当于重新设计精确匹配规则。

### 5.2 候选预算

否定移出 FTS 后,候选集合变宽,前 200 组可能全部被复核排除,结果页出现空白但不提示。这是策略
问题,不该混在语义修复里静默改变。

建议:

- `SearchResponse` 增加状态字段,至少区分「候选未复核完」与「已复核结果被展示上限截断」。
  仅比较候选数与返回数无法判定前者,`src/bin/cli.rs:414` 现有的判断也要替换;
- `total_documents` / `total_groups` 的文档与 UI 文案改称「候选」,与「已验证结果数」区分;
- **P2 就要带上「未穷尽」状态与候选计数文案**。否定一旦移出 SQL,候选增宽立即发生,不宜等到
  P3 才提示;P3 保留 200 组并加状态并不必然改变「不补页」的契约,只有继续扫描才会;
- 继续扫描需要稳定排序与游标,并固定一次查询的词典与 plan;预算是**内容组数**,不能误变成
  文件位置数。本轮不必再做独立的全量模式。

## 六、P4:tokenizer v2

把每个非空白分隔符(标点、emoji、其余非字母数字)也作为单码点词元索引:

```text
文、档  →  [文, 、, 档]
文 档   →  [文, 档]
```

FTS5 短语语义是词元序列连续出现,于是 `"文档"` 命中 `文 档`、不命中 `文、档`;FTS 的布尔运算
是文档级集合运算,叶子精确则整个表达式精确。这个方向与 `src/tokenize.rs` 里记录的已知差异
(emoji 与部分符号在 `simple` 里各算一个词元,在 rsou 被丢弃)一致,可把该差异一并收掉。

它**不能完整解决 B6**:能收掉纯 emoji / 符号零词元这一部分,但 ASCII 子串与跨 ASCII 空白
依旧。也**不能**修:非法 NOT 语法、前置否定的布尔转换、字段覆盖、计数与高亮混用。因此 P4 落地
后仍需保留 plan 复核。

需要先测再决定:

- 索引体积分 FTS、整库、重建临时空间三项测量,「涨 10–30%」目前没有数据支持;
- BM25 的文档长度与平均长度都会变,排序变化会改变进入前 200 组的集合,不能预先认定可忽略;
- 迁移:`src/store.rs:30` 升到 5;`can_upgrade_from`(L201)当前只接受 `2`/`3`,要纳入 `4`;
  `drop_legacy_fts`(L213)以 `documents_fts_content` 影子表判定旧格式,对 tokenizer 参数变化
  不适用,需要可靠的格式标识(避免脆弱的建表 SQL 字符串包含判断);
- tokenizer 构造器(`src/tokenize.rs:101`)当前只接受 `0`/`1` 且不保存模式状态,迁移期间读旧表
  仍要能实例化旧参数;
- 源码里多处注释写「与 wsou 的 `simple 0` 同语义」(`src/tokenize.rs:1`、`src/tokenize.rs:102`、
  `src/store.rs:350`)。wsou 是另一个产品,这些注释是移植期的对照记录;rsou 的语义应以自身的
  设计规范与测试为准。P4 落地后,这类对照注释要么删掉,要么改写为具体行为差异。

## 十、复杂性根源与简化路线

### 10.1 根源:两套匹配规则不一致,高亮又承担了查询判定

FTS 检索与独立高亮可以共存。当前问题在于:FTS 按词元、字段和布尔条件匹配,定位器按
「忽略空白的子串」匹配,而复核丢弃查询结构后,仅凭任意高亮区间存在就让文档通过。

这些缺陷分为三类,不能指望删除某一层就全部消失:

- **结构错误**:AND 退化为任意词命中、字段混用、否定错编译。需要正确保留和执行查询结构,
  更换 tokenizer 不能根治。
- **语义冲突**:ASCII 词元边界与子串不一致,标点、空白的处理也不同。这是两套机制长期并存的
  主要维护成本,必须决定哪套匹配规则是最终标准。
- **实现错误**:只定位第一处、截断后计数。即使只有一个搜索引擎,仍需正确枚举和统计。

简化应从确定最终匹配语义开始。减少模块数本身不能保证正确性。

### 10.2 可选路线及代价

| 路线 | 收益 | 风险与前提 |
| --- | --- | --- |
| FTS 为唯一匹配标准,应用层只展示高亮 | 取消应用层精确复核、候选超集证明和扫描退路;计数、排序与分页更直接 | 接受词元边界语义;不再承诺 ASCII 子串与内部跨空白匹配;若仍要求中文标点敏感,必须调整当前 tokenizer |
| 应用层扫描为唯一标准,删除 FTS | 布尔判定、定位和高亮共用一套规则;没有索引候选欠召回 | 每次搜索可能读取整个资料库的正文;延迟、取消与排序需要重新设计,失去现成 BM25 |
| 保留 FTS,统一 Plan 与叶子扫描 | 保留声明语义,修复结构错误;无需立即迁移索引 | 仍需不安全叶子的退路、复核预算与性能控制;对应本计划 P1–P3 |
| 所有非空白字符逐码点索引 | 更接近统一的忽略空白子串语义,包括 ASCII;减少索引与复核的差异 | 索引体积、英文排序和性能变化需实测,并需全量迁移;这是比 P4「增加符号词元」更大的改造 |

「直接改用 FTS 自带高亮」也需要额外工作。当前 `documents_fts` 为 contentless-delete 表,
不保存可供 `highlight()` 返回的标题与正文。要取得与 FTS 匹配严格对应的展示区间,需要调整
内容接线或增加位置提取机制。后者的存储、SQLite 集成与维护代价也应纳入路线评估。

### 10.3 当前建议:先做保守简化

沿用第八节的决策,将职责收拢为三件事:

1. 一棵查询树决定文档是否匹配;
2. 一个叶子扫描器提供匹配位置,真假判定、片段与预览共同使用;
3. FTS 只安全地缩小待检查范围,不承担另一套最终判定。

对应的删减已经可以落进 P1/P2:删除独立的 `compile_exclusion`,不强制 NNF,合并直接匹配与
空白匹配扫描,取消预览对扁平 literals 的独立判定,统一命中计数口径。

这能降低逻辑重复与维护成本,但不会消除 FTS 与子串语义不一致的固有成本。P3 的安全退路与
候选预算仍然必要,不能把保守简化描述成完整消除了双机制。

### 10.4 更根本的备选:收窄语义,由 FTS 唯一判定

如果 ASCII 子串、跨空白编号与纯符号检索不是核心需求,可以将产品明确为文档关键词检索:

- 中文按连续词元匹配,标点打断连续性;
- ASCII 按词元边界匹配,不承诺英文或数字内部任意插入空白仍能命中;
- 宽松模式负责拆词,字段与布尔条件由统一编译结果决定;
- 纯符号是否支持单独定下,不再把应用层能找到子串等同于查询应当命中。

在索引规则与产品语义对齐后,应用层安全退路、全表扫描及复核预算的大部分复杂性可以取消。
展示上限和普通分页仍然存在,parser/compiler 正确性、完整高亮与计数测试也仍须保留。
查询树、字段解析、同义词展开与合法的否定编译仍然需要;高亮遵循新的词元与字段规则,
不能再用字符扫描所得 span 是否存在来反向决定文档是否命中。
代价是放弃部分 PDF 排版容错、编号子串与符号检索能力,并完成 tokenizer、迁移和高亮接线调整。

该路线目前是备选,不覆盖第八节已定的保守修复方向。只有决定接受上述产品语义变化后,
才应改写 P2/P3 的实施范围;不要同时维护两种「精确模式」来回避这个选择。
