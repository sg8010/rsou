# 搜索决策单一化

本决策已由 `7ffc5cb` 实现，原始任务书收录于 `478cf30`。本文是维护用的压缩版本；
原任务书与旧方案可通过 Git 历史查看；后续反例和验收线索见
[搜索已知问题](search-known-issues.md)。旧方案的应用层复核、Plan evaluator 和补召回不再作为实施要求。

## 1. 决策

**全文条件由 SQLite FTS5 `MATCH` 判定，结构化条件由 SQL 过滤；展示定位不再否决搜索结果。**

旧实现会在 FTS 命中后，因 `locate_literals()` 返回空结果而丢弃文档。
该定位器只扫描正向字面量，不能完整复核布尔和字段语义，且与 tokenizer 的规则不同。
现在它只负责高亮和导航，搜索路径为：

```text
query.rs / jieba / 同义词 → MATCH 表达式
→ FTS5 MATCH + SQL 结构化过滤
→ content_hash 分组、BM25 排名、结果限量
→ 读取正文 → 快速 Locator / chunks / Hit → GUI 结果列表
→ 用户打开文档 → 异步读取原文 → 完整 Locator → 预览高亮与导航
CLI 仍走完整定位
```

这次修改统一了判定职责，但不保证查询编译、tokenizer 或排名本身没有问题。

## 2. 行为变化与保留范围

| 场景 | 当前行为 |
| --- | --- |
| 搜“文档”，原文为“文、档” | FTS 命中，文档保留；Locator 无高亮 |
| FTS 命中，但只定位到部分正向字面量 | 保留文档，展示能定位到的部分 |
| FTS 因索引漂移命中原文不存在的词 | 仍返回结果，需重建索引消除漂移 |
| FTS 没有命中，但字符串扫描可能找到子串 | 不通过应用层扫描补召回 |
| 正常命中 | 继续生成标题高亮、正文片段和预览导航 |

精确模式继续生成 FTS phrase / MATCH；宽松模式继续由 jieba 改写查询。
同义词仍在查询阶段展开。这些机制均保留，不新增应用层查询求值器。

最初的搜索决策单一化不改变 tokenizer、查询语法、数据库 schema、contentless-delete、分块、
`bm25(5.0, 1.0)` 权重，也不新增分页或 snippet；后续 B3 采用两阶段定位，B2 区分快速列表已定位数量与完整片段总数。

## 3. 不变式与边界

- `locate_literals()`、高亮 Span、Hit、fragment 和 chunk 均属于展示数据。
  它们为空或定位不完整，不得成为 `continue` / `retain(false)` 剔除结果的理由。
- “不得因定位为空剔除”不等于返回所有 FTS 命中文档：仍有结构化过滤、排名和展示上限。
  文档已删除、正文缺失时仍沿用跳过行为；正文读取或转换错误仍按存储错误处理。
- `MAX_RANKED_GROUPS = 200` 表示最多读取排名靠前的 200 个内容组。
  `max_documents` 默认展示 100 组，同组文件位置不额外占组名额；不继续补页。
- `total_documents` / `total_groups` 统计满足 MATCH 与结构化过滤的文件位置数 / 内容组数，
  不受展示上限影响，也不代表所有命中均已读取并返回。
- chunk 查询失败等展示问题尽量降级；Locator 无 span 不算搜索失败，最多记录 debug 日志。
- GUI 列表显示“展示 N 个相关片段”，不声明全文总数；无正文定位但有标题高亮时显示“标题命中”；
  两者均无时隐藏命中数。空定位结果仍可点击并加载原文，默认从文首预览。
- 预览先异步读取 `plain_text` 并显示，再完整定位；缓存完整区间与片段偏移，窗口高亮从缓存截取，导航不受列表 Hit 上限限制。

## 4. 验收

| 回归场景 | 必须满足 |
| --- | --- |
| FTS 命中、Locator 为空 | 文档仍在结果中，允许标题高亮和正文 Hit 均为空 |
| FTS 命中、部分 literal 可定位 | 不因其余 literal 无定位而丢弃文档 |
| 普通命中 | 高亮字节区间、片段及标题定位保持正常 |
| SQL 结构化过滤 | 计数、分组及返回结果采用同一过滤口径 |
| content_hash 分组 | 同组命中文件位置保留，代表位置按相关度选择，空定位不拆组或丢位置 |
| 排名和展示上限 | 默认 100 组，最多处理前 200 组，不读取后续组补位 |

主要自动化覆盖位于 `src/search.rs`、`src/maintain.rs`、`src/tokenize.rs` 和
`tests/search_candidates.rs`。核心验证命令为 `cargo test -p rsou`；
GUI 的空定位卡片点击、全文加载与导航由用户手动验收，单测通过不能替代交互验收。

### FTS 与 Locator 的语义差异

tokenizer 将标点视为分隔符且不产生词元，因此“文、档”可以满足短语“文档”；
Locator 在原文上按字面量定位，不剔除标点，所以可能没有高亮。
空白或换行可被 Locator 忽略；列表只补首处，打开文档后完整定位；不额外枚举重叠出现。

后续可以让展示定位更贴近 FTS 语义，但不得重新授予 Locator 搜索否决权。

建议顺序：查询正确性 → 定位与导航 → 计数及文案 → tokenizer 与排名。
分页和预览性能按产品需求独立安排。
